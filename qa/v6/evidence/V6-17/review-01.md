## Blockers

1. **The `support` stage does not perform support matching, and generated AST support links are empty.** S04 defines support as matching specification evidence. `generation.ts:51-57` maps it to `assess_readiness`, whose output is a readiness/coverage/gaps report; `audit_support` runs later as a dependency of `checks`. An independent run with `CountingProvider` showed `supportOutputKeys=[readiness,coverage,dimensions,gaps]`, while the generated claim feature had `factIds=[]` and `supportParagraphIds=[]`. The same AST builder also emits empty `sourceRefs` and `factIds` for paragraphs. In addition, `currentInput` (`generation.ts:733-761`) omits the persisted `snapshot.facts` from `PipelineContext`; those facts affect the input hash (`:769-783`) but are not supplied to generation. This makes the five-stage display materially misleading and drops confirmed-fact traceability. The pipeline did run both `draft_specification` and `draft_abstract`, plus figure generation, and `checks` ran `audit_support`, `audit_consistency`, and `audit_formal_rules`; those mappings are real, but do not repair the missing support stage.

2. **Configured job cost and duration ceilings are not enforced as job limits.** `maxCostMinor` is only checked for a positive integer (`generation.ts:280-283`) and is never used to stop or constrain provider calls; invocation costs remain null. With `maxCostMinor=1`, an independent run succeeded after 13 provider calls. The duration check (`:983-1000`) measures each logical stage separately, not the whole job: with `maxDurationSeconds=1` and 130 ms per provider call, the job succeeded after 13 calls in 1,787 ms. S04 requires these limits on generation jobs and `JOB_LIMIT_EXCEEDED` when exceeded. The receipt's “no quota accounting” limitation does not cover the configured per-job cost cap.

3. **Generated revisions store the input hash as `DraftRevision.astHash`.** Adoption passes `record.job.payloadHash` to `saveRevision` (`generation.ts:1524-1530`), but this is the input hash, not a digest of the AST. An independent adoption probe found `revision.astHash === job.payloadHash` and a different SHA-256 for the canonical generated AST. The edited-revision seam correctly computes an AST digest (`:533`), so generated and edited revisions currently assign different meanings to the same contract field.

4. **The V6-18 revision seam cannot recover a post-commit state-write failure.** `saveEditedRevision` writes the revision row, commits the target pointer and `revision.created` event, then separately writes the revision-state row (`generation.ts:558-590`). I injected a one-time failure on that final `revisions/` write. The method returned failure although `loadHeadRevision` showed the new edited revision as the target head; the next save using that head returned `VERSION_CONFLICT` because the stored revision state still named the old head. The receipt discloses the pre-commit orphan-row window, but not this post-commit unrecoverable state mismatch. The basic head/load, DraftAST validation, base check, matter-version CAS, and event paths are present; this failure prevents treating the seam as ready for V6-18.

5. **The S04-A07 receipt observation names the wrong failing stage.** `receipt.json` says the support stage failed, but `generation.test.mjs` injects invalid output for `draft_claims`; the assertions show facts and support completed and the logical `claims` stage failed. Correct this observation so the acceptance evidence describes the executed case.
