# V6 原型对齐：独立浏览器验收准备

状态：**仅完成准备，尚未启动服务或浏览器验收**。收到 Lead 明确的「可开始验收」后，使用现有 Claude Code + executor，在该工作树的集成结果上运行 `browser-acceptance.py`。本文件和脚本是本次唯一写集；不改产品代码，不操作 IndexedDB，不绕过检查、确认或导出门禁。

## 验收环境与记录

- 工作树：`.claude/worktrees/v6-prototype-alignment/`，基线 `e9723cc`。验收时先确认开发者已完成并由 Lead 指定服务端口、应用 URL 与运行方式；不在三位 developer 仍写共享工作树时启动服务。
- 使用独立、临时 Playwright BrowserContext。一个验收过程内保持同一 context，以便真实检查 reload 后的 IndexedDB 状态；不预置、读取或写入 IndexedDB，不调用应用内部 API，不注入业务状态。所有业务写入均通过真实页面控件完成。
- 上传路径使用仓库现成合成材料 `qa/v6/scenarios/V6-13/fixtures/intake-source.txt`。该文件含相互冲突的公开历史陈述，用于观察产品真实规则的结果。无文档路径使用单独新建的空案件，选择「没有现成文档，直接回答问题」，不得生成虚拟附件。
- 页面动作、URL、关键正文、DOM 可见状态、截图、下载文件、pageerror 和 `console.error` 保存到脚本输出目录。失败、门禁阻断和无法制造的状态均记录具体页面与前置条件；不得为了让后续步骤通过而跳过或伪造确认。

## 场景与通过标准

### 1. 两种进入材料路径

1. 从首页创建空案件，检查 URL、案件列表和动态；进入上传步骤，点「没有现成文档，直接回答问题」。确认无来源文件或虚拟附件，进入五题。
2. 再从首页创建另一空案件，上传上述合成 TXT，通过页面的保存/解析步骤进入五题。确认材料名称、保存状态与真实解析段落来自该文件。
3. 若上传失败，保留文件行、状态和错误证据；不把未保存文件当作成功，不改用程序写存储。

### 2. 五题逐题保存与重载

问题顺序按界面实际顺序记录：问题、区别、发明人、公开历史、成熟度。

- 每题使用明确的 QA 内容；直接回答路径给每题选「用户直接回答」，上传路径只选界面实际提供、且能定位到解析材料的来源；证据不足时如实选择「材料中未找到」或记录未完成，不伪造材料引用。
- 发明人通过页面按姓名添加/选择一位仅用于验收的合成人员；不输入人员 ID。公开历史、成熟度由操作者显式选择，验证初始状态没有预填。
- 每题保存后记录答案、来源和版本，再对当前 URL 执行真实页面 reload，确认已保存值仍可见，再进入下一题。若页面不支持逐题提交或 reload 丢失值，记录实际表现和页面状态，不切专业页补写数据库。

### 3. 按名称选路线与创建真实目标

- 在自助路线步骤用路线显示名称选择（默认按产品能力选择「中国实用新型」）；以人员姓名选择发明人。不得填写人员 ID、直接改 URL 绕过路线页面或构造目标数据。
- 通过页面「创建/保存目标」动作创建目标。记录保存前后目标列表、显示路线、人员姓名、URL 和真实 `targetId`。刷新目标页确认目标仍存在。

### 4. 本地 stub 生成与采纳

- 进入专业流程前，先通过事实页 UI 新增一条明确标记 `【合成验收事实】` 的测试事实；来源绑定到本次上传 fixture 的真实解析段落，状态由操作者选为「用户确认」。该事实只用于制造可核验的验收输入，不代表用户真实发明；保存后 reload 验证仍在。只有目标图集为空时才通过材料页 UI 导入并绑定一张脚本生成的「验收合成图」PNG。
- 在自助和专业入口中观察实际生成执行引擎提示；运行时应明确标出这是本机 stub/测试生成，不得称真实 AI 或外部模型结果。
- 通过页面启动生成，记录实际任务阶段、错误、候选内容和测试标记。仅当页面提供且启用「采纳」动作时点击，并确认新修订在同页编辑/审阅视图可见。
- 记录 `testOutput` 标记在生成完成后 reload 恢复、采纳后的修订、标题修改并保存、正文段落修改并保存、编辑器重新载入（恢复）、自助预览中的状态。任一步标记消失或变为 false 都记录为失败；不可用标题或手工编辑把测试修订伪装成正式修订。
- 若生成入口被 blocker 禁用、没有可用执行引擎、任务失败，或候选标为不可采纳，记下按钮 disabled 状态/提示和当前门禁原因；停止依赖该修订的步骤，不换引擎、不造输出、不写 revision。

### 5. 检查、风险确认持久化与旧确认失效

- 对当前目标运行产品提供的检查。记录规则包版本、检查运行 ID、SnapshotRef、四级 finding 及其操作。
- 若真实检查结果包含要求确认的风险，通过对应「确认风险」控件确认一项；记录确认后的 UI 状态，刷新同一 URL，再记录确认是否仍在且仍绑定同一风险/检查/快照。
- 随后通过草稿编辑器修改一个真实段落并保存为新修订。返回检查/审阅页面，记录旧确认是否标为陈旧或失效；按页面要求重新检查后确认旧记录没有被当作新快照的有效确认。
- 若规则没有产生需确认风险，明确记录检查结果中风险数量/类别/原因，以及无法执行 reload 持久化验收；不更改规则包、不编造风险、不写确认 ledger。

### 6. 自助通读与专业逐段确认

- 在自助预览逐页实际阅读候选内容，通过页面勾选并提交通读确认；记录保存后状态。刷新同一路径，确认状态仍在且对应当前 SnapshotRef。
- 在专业草稿页检查编辑器和逐段审阅是否同页可用。对所有真实显示的 AI/混合段落逐段阅读后分别确认，记录总段落数、确认数和当前修订；刷新后核对。
- 两类确认分别通过各自界面完成，不能用一类确认代替另一类。若没有可采纳修订/没有 AI 段落，记为前置阻断。

### 7. 批准、门禁更新与实际下载

- 到交付页记录批准前的批准门禁和导出门禁。只有当真实门禁允许时，才通过「记录内部批准」页面动作批准；不使用任何强制导出方式。
- 检查批准结果是否在当前页面即时反映到批准记录和导出门禁，无需整页刷新。若仍有 blocker，保留各 `code` 和「去处理」路径。
- 若合法门禁指出缺少附图，通过「材料 → 导入附图 → 编入图集」实际导入并绑定一张脚本生成的 PNG。图上清楚写「验收合成图」及“仅用于测试”，不代表用户真实发明。只有目标图集为空时才追加这张测试图；绑定会改变快照，之后必须按新版本重新生成/检查/确认/批准。
- 若门禁指出验收事实尚未确认，只能在事实页用 UI 对明确标注 `【合成验收事实】`、且引用已上传 fixture 原文的测试事实执行用户确认；保存后重新生成并完整重走受影响的门禁。不可把未知或真实用户事实标成已确认。能通过页面正常修复的阻断要继续重试到下载；不能修复的逐项记录具体门禁码、资源、页面和已尝试动作。
- 门禁允许后使用临时验收口令创建真实导出，监听浏览器 download，并保存落盘。验证下载 ZIP 可读取、`testzip()` 无损坏；对其中 DOCX 检查 OOXML 必要项和 XML 可解析，对 PDF 检查 `%PDF-` 头；检查公开清单/文件内容中的测试输出标记仍明确存在。对 patentpack 检查加密信封形状且不输出口令/敏感明文。
- 记录 CN XML 的 `FORMAT_UNAVAILABLE` 和解释。它表示 XML 不可用，不代表已递交；不得将导出包描述为已签署、已递交或官方回执。

### 8. 专业工作台、全局动态与视觉状态

- 生成修订后检查专业草稿编辑器与逐段审阅面板同时出现；记录两个 DOM 区域和 bounding box，确认能在同一页面读写/审阅并可定位对应段落。
- 至少创建两个案件后打开全局动态，确认新事件能跨案件出现；回到页面后再操作一次并验证动态内容/计数更新。所有文本必须来自真实活动记录。
- 在「设置」通过界面选择「原生」主题和浅色/深色模式；另以 `prefers-color-scheme` 模拟系统浅/深，记录根节点 `data-theme`、`data-mode` 和截图。
- 在首页、五题、草稿、检查、交付、动态、设置等代表页以 390px viewport 采集截图和 `scrollWidth`；记录横向溢出与无法操作的控件。
- 汇总所有 `pageerror`、`console.error`，不以“没有控制台错误”代替业务通过。

## 操作约束与停止条件

- 不读取或修改 `window.indexedDB`、不注入 browser storage state、不执行页面 JavaScript 修改业务数据；脚本内 `evaluate()` 仅读取可见 DOM/尺寸。
- 不 npm install、不连真实 AI、不发送真实外发授权、不收费、不签署、不递交。生成和导出限于产品明确标出的本地测试输出。
- 只有 Lead 给出「可开始验收」后才启动服务和脚本。遇到共享工作树还在变化、授权拦截、服务未就绪或 UI/脚本前置条件不成立时，记录后停止相应链路并报告，不绕行。
